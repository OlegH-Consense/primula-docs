# Primula documents

Primula is a plain-text markup for business and technical documents. The translator
`primula` turns a `.prml` file into an ODT (and PDF through LibreOffice). Commands start
with `|`; a small Python subset computes values; styles live in styles modules; a project
file holds shared parameters and build targets.

You are not guessing: the translator checks everything. **Write, then run
`primula check`, then fix every error by its code, until the check is clean.** Never hand
over a document that has not passed the check.

## 1. Find the translator

Try in this order and use the first that works:

```sh
primula --version
<primula-docs>/primula --version                              # launcher of a source checkout
PYTHONPATH=<primula-docs>/src python3 -m primula --version   # the same without the launcher
```

A Primula Studio installation ships the translator too (its `primula` is in the
installation `bin/` directory or set in Studio → File → Settings). If none is available,
say so and still follow the rules below, but state that the document is unchecked.

## 2. Learn the context before writing

- **Project.** `project.p.prml` is found upwards from the document. It gives parameters
  (`params:` → names in the text), `doc_defaults:` (metadata defaults), `keys:` (key map for
  `|include(key=…)`, `|img(key=…)`), `ref_documents:`, `styles:`. Read it.
  `primula check project.p.prml --dump-project` prints it as JSON.
- **Styles available** (names for `|.Name:`, `|.Name{…}`, `style=`):
  `primula check FILE --dump-styles` → JSON, `.styles.styles[] | {name, kind}`.
- **Structure and IDs** for `|@("id")`: `primula check FILE --dump-structure`.
- **Reference of the language, generated by the translator** (always current, prefer it to
  memory): `primula commands --format json --lang en` — `commands`, `short_forms`,
  `closings`, `functions` (signature, arguments, example), `header_keys`. Text forms:
  `primula commands`, `primula commands --functions`, `primula commands --header`.
- **Specification** (Russian, normative): `primula-spec-v1.1-draft.ru.md`,
  `primula-stdlib-v1.1-draft.ru.md` in the source tree; sections are cited in the reference
  as `[§ 8.2]`.
- The compact syntax overview of this skill: [references/syntax.md](references/syntax.md).
- A complete checked document: [assets/contract.prml](assets/contract.prml).

## 3. The check loop

```sh
primula check FILE --format json --lang en      # diagnostics as a JSON list; exit 2 on errors
primula check FILE --lang uk                    # the same as text, in the user's language
primula build FILE -o out/FILE.odt --pdf        # when the user wants the output
```

Each diagnostic has `code` (`P` + 4 digits), `severity`, `message`, `file`, `line`,
`column`, `notes`. Fix errors first, then look at warnings (a warning often means a real
problem: unformatted number or date, direct formatting). Codes by first digit: P0 CLI/IO,
P1 syntax, P2 names/core, P3 styles, P4 structure/references, P5 tables, P6 pages/graphics,
P7 modules/project, P8 ODF, P9 technical documentation.

Unsaved text of another file can be checked without writing it: `--overlay FILE=BUFFER`.
To try an expression or a library function quickly: `primula console [FILE]`
(`:help name`, `:functions text`; `math` is available there without import).

## 4. Writing rules that matter most

1. **Header.** A document starts with a YAML header between `---` lines. Metadata go under
   `doc:` (`title`, `language`, `creator`, `created`, …); parameters under `params:`.
   `document:` and `documents:` are old names — error P1120. The header has no expressions.
2. **What follows `|`.** A letter — a command (`|toc`); `(` — an expression `|(x)`;
   punctuation — a short form (`|>`, `|*{…}`); `||` — a literal bar. A space, digit or end
   of line after `|` is an error. A letter right after a command name continues the name:
   write `|seller|;ом`, not `|sellerом`.
3. **Structural short forms only at the start of a line:** headings `|<` … `|<<<<<<`,
   clauses `|>` `|>>`, list items `|-` `|#`, admonitions `|!("note")`, table rows `|:`.
   A line form ends at the end of the line; several paragraphs need an environment
   (`|>: … |end>`).
4. **Closing.** `|end` closes the nearest environment, but not `|if`/`|for`/`|def` — those
   close with `|endif`, `|endfor`, `|enddef`. A code block `|code:` closes with a bare `|end`
   line (not `|end code`).
5. **Values in text.** `|(expr)` prints a value as text. It must be a string, a number, a
   date or markup: `None`, `bool`, lists and records are errors (use `str()`,
   `join_list()`). Format fractional numbers, money and dates with the library (`num`,
   `money`, `money_full`, `fmt_date`) — a raw float or date gives a warning. Money is
   `decimal`: `dec("0.20")`, never a float.
6. **Code** is a Python subset (no `import`, `class`, `try`, `lambda`, …). Definitions at
   the top level are lazy and immutable. An f-string must not contain the same kind of
   quote inside its braces. `std/math` needs `|import("std/math")` in a document.
7. **Styles.** `|.Name{text}` — character style; `|.Name: text` (at line start) — paragraph
   style for the line. Use only names that exist (`--dump-styles`); prefer styles to
   direct formatting `|fmt(…)` (it warns). Without a project's styles, name a styles set
   of the kit in the header: `styles: [std/styles/business]` (contracts, acts),
   `letter` (official letters), `technical` (manuals), `report` (reports after DSTU 3008),
   `compact` (memos). An own styles module builds on a set with `extends: std/styles/business`
   and holds only the differences.
8. **References.** Give targets an `id=` (`|<(id="price")`, `|>(id="pay")`,
   `|table(id=…)`, `|appendix(id=…)`) and refer with `|@("pay")`, `|@("pay", "label")`.
   Never type clause numbers by hand.
9. **Language.** Set `doc.language` (`uk-UA` by default for Ukrainian business documents);
   library functions take `lang=` and follow the document language: quotes `|"{…}`,
   `fmt_date(d, "contract")` → «12» жовтня 2026 р., `money_full(x, "UAH")` (amount in
   words), `plural(n, "день", "дні", "днів")`, `words(n)`.
10. **Files.** UTF-8, LF. Paths are relative to the file and stay inside the project root.
    Suffixes: `.prml` document, `.f.prml` fragment (`|include`), `.m.prml` module
    (`|import`), `.s.prml` styles module, `.p.prml` project.

## 5. Editing an existing document: what you must not change

When the task is proofreading, translation, rewording or "fix the grammar", change **only
the text the reader sees**. Keep byte-for-byte:

- command names and the form of every construct (`|<`, `|>`, `|table … |end table`);
- **style names**: `Місце-дата` in `|.Місце-дата: …` is a style, not a caption — changing it
  to `|.Місце і дата:` breaks the document (P1209);
- argument values that are identifiers: `id=`, `key=`, `style=`, `ns=`, `part=`, page
  style names, format names (`"contract"`), currency codes;
- names in expressions: parameters, record fields, functions, macros
  (`|(замовник.обʼєкт)` keeps its U+02BC apostrophe even if the text uses `’`);
- comments `|%`, code blocks, `|verbatim` content, the YAML header keys.

Do not change the meaning of legal or technical text when asked for grammar or spelling
only; propose such changes separately. Report edits as "line N: before → after". After
editing, run the check: it must give no new diagnostics.

## 6. Creating a document

1. Ask for or infer: document type, parties and requisites, dates, amounts, language.
   Do not invent real company data, codes (ЄДРПОУ, IBAN) or signatures — use parameters
   and placeholders `|?{…}` where data is missing (`--strict` turns placeholders into
   errors before release).
2. Put changing data into `params:` of the header or the project, not into the text.
3. Start from [assets/contract.prml](assets/contract.prml) or a template of the project;
   keep the structure: title heading without number → place and date → preamble →
   numbered sections `|<` with clauses `|>` → requisites and signatures.
4. Check, fix, check again. Build when asked; to look at the result, convert the PDF pages
   to images if you can view images.

## 7. Frequent mistakes

- **P1224 code block not closed** — cause: `|end code` after `|code:`; fix: a bare `|end` line.
- **P1209 `|.X` needs a body** — cause: text changed after `|.Style`; fix: restore the style name, or `|.Style{text}`.
- **P2201 name not defined** — cause: typo, or `math.*` without import; fix: check `params:`, project parameters; `|import("std/math")`.
- **P1120 header key renamed** — cause: `document:` / `documents:`; fix: `doc:`; in a project `doc_defaults:`, `ref_documents:`.
- **command swallowed a word** — cause: `|nameом`; fix: `|name|;ом`.
- **`|end` does not close `|if`** — cause: control constructs; fix: `|endif`, `|endfor`, `|enddef`.
- **warning on a number or date** — cause: raw value in `|(…)`; fix: `num()`, `money()`, `fmt_date()`.
- **float in a money function** — cause: binary float; fix: `dec("…")` or a decimal literal.
- **level skipped** — cause: `|<<<` after `|<`; fix: go one level at a time (also for lists).

## 8. Images computed by code

`|img(svg=text)`, `|figure(svg=text, …):`, or an image value `img(svg=…, height="10mm")`
passed to `|img(value)` / `|figure(value):`. The SVG string must have a root `<svg>` with
a size, no DOCTYPE/ENTITY, and only `#…` or `data:` references (P6110–P6112). Use it for
charts, QR codes and bars produced by a module function.
